---
title: Resource sharing
description: Ask auth-service whether a user may use a shared resource, list what they can reach, and report the validation or loss of ownership of a resource you own.
---

auth-service lets a user or an application **own** a resource (a model, an agent, an MCP server, an SSH account, or a resource of a scheme your application defines) and **share** it with users, organisations, plans or every member of the application. The decision is always auth-service's: your code asks and obeys. Concepts and operator side: [Resource sharing](https://docs.circle-cyber.com/auth-service/docs/project/resource-sharing-final-design) in the auth-service documentation.

The calls below come from two clients: `machine.resources` for the application's backend, and
`user.resources` for the signed-in user's own resources. The decision is always auth-service's:
your code asks and obeys. Concepts and operator side: [Resource sharing](https://docs.circle-cyber.com/auth-service/docs/project/resource-sharing-final-design) in the auth-service documentation.

## Prerequisites

- auth-service runs with `RESOURCE_SHARING_ENABLED` on, and sharing is enabled for the application that offers the resource. Without it the routes do not exist and every call throws `API_001` with `details.status` `404`.
- A **confidential** application, as for the rest of the machine API.
- `resourceSharing: true` in `createAuthClient` for the self-service client: it asks for the
  `resources:self:manage` scope and the auth-service audience at sign-in, so the user must
  sign in again after the option is turned on.
- The machine scope of what you call:

| You are | Scope | Calls |
| --- | --- | --- |
| The validator bound to a resource scheme (your application owns the scheme) | `resources:validate`, given to new confidential applications | `validate`, `invalidate` |
| An enforcement point that admits users to resources | `resources:authorize`, granted by a superadmin | `authorize`, `listAccessible` |
| A metering component that reports what a provider billed | `resources:usage:write`, granted to the platform's metering components only | `recordUsage` |

Every decision is taken for the **application whose credential you use**: it sees the resources that application owns and the ones shared with it, never everything a user owns. A missing scope makes the call throw `TOK_004` with the scope in `details.scope`.

## Admit a user to a resource

```ts
import { createBearerVerifier } from "@circle-rd/auth-ai/server";

const verifier = createBearerVerifier(auth, { audience: "https://api.example.com" });

const token = await verifier.verifyHeader(request.headers.authorization);
if (token.userId === null) throw new Error("A user token is required");

const decision = await machine.resources.authorize({
  subjectId: token.userId, // the verified `sub`
  actorClientId: token.clientId, // the verified `azp`, kept for audit
  resourceUri: "gine://project-42",
  audience: "https://api.example.com",
  permission: "write", // `read` by default
  requestId: request.id,
  source: "external",
});

if (decision.decision !== "allow") throw new Error("Forbidden");
console.log(decision.accessKind, decision.permission); // "owner" or "grant"; "read" or "write"
```

- **Take `subjectId` and `audience` from a token you verified**, never from a request body: auth-service trusts them as they come. `actorClientId` only labels the access log; the calling application is your machine credential.
- **Fail closed.** Only `decision: "allow"` is an admission. A denial carries no reason, so it cannot be used to probe which resources exist, and an `authorize` that throws (`API_001`, `API_002`, a timeout) is a denial too.
- **`write` covers `read`.** Ask for the level the request needs: a `read` grant is refused when you ask for `write`. The answer carries the level the user holds, so an interface can show or hide actions without trying them.
- Ask for every request that needs it: the answer reflects revocations, bans and membership changes at once, so do not keep it longer than the request.

## List what a user can reach

```ts
const resources = await machine.resources.listAccessible("user-sub", { scheme: "llm" });
for (const resource of resources) {
  console.log(resource.resourceUri, resource.accessKind, resource.permission);
}
```

The list holds what your application owns and what was shared with it. Use it to filter what you show, and call `authorize` for the decision itself.

## Validate a resource you own

When an owner asks to validate a resource of a scheme your application defines, auth-service marks it pending and waits for your answer. You prove the ownership your own way (the project belongs to the caller, the object exists), then report:

```ts
await machine.resources.validate(resourceId, {
  result: "validated",
  evidence: { checkedBy: "my-app" },
});

await machine.resources.validate(resourceId, {
  result: "validation_failed",
  reason: "This project belongs to another account",
});
```

`reason` is shown to the owner. `evidence` is stored with the resource: never put a secret in it.

When ownership is lost later (the project was deleted, a host key changed), disable the resource so access stops at once:

```ts
await machine.resources.invalidate(resourceId, "project-deleted");
```

Only the client bound to the resource's scheme may call `validate` and `invalidate`; another client gets `API_001` with `details.apiCode` `AUTH_011`.

## Report the usage of a resource

A metering component reports what a provider billed for a resource. auth-service owns accounting; this is the only write and reading stays with it.

```ts
const receipt = await machine.resources.recordUsage({
  decisionId: decision.decisionId, // from the `authorize` that admitted the request
  startedAt, // when that request started
  resourceId,
  resourceUri: "llm://acme/gpt-x",
  requestId: eventId, // 64 lowercase hex characters, stable per event
  occurredAt: new Date(),
  usageSource: "provider",
  costUsd: "0.0042",
  promptTokens: 120,
  completionTokens: 30,
  totalTokens: 150,
});
```

Replaying the same event is safe: `receipt.replayed` is `true`. Use `usageSource: "unsupported"` with no cost and no tokens when the provider reports nothing. The `decisionId` names the person and the application, so a usage event cannot claim another one; it lives 60 seconds and only the client that obtained it may present it. A payload that conflicts with the stored event is refused with `RES_012`, a caller with no access to the resource with `RES_011`, and a decision that is expired, forged or issued to another client with `RES_016` (all `API_001`).

## The user's own resources

`ai.forUser(grantId).resources` is the self-service client. It uses the user's access token,
never the application's: an application acts only on what that user owns or administers.
Turn it on with `resourceSharing: true` in `createAuthClient`.

```ts
import { createAiClient } from "@circle-rd/auth-ai";
import type { AuthClient, GrantManager } from "@circle-rd/auth-ai";

declare const auth: AuthClient;
declare const grants: GrantManager;
declare const grantId: string; // the signed-in user's `sub`

const user = createAiClient({ auth, grants }).forUser(grantId);

const applications = await user.resources.listMemberApplications();
const organizations = await user.organizations.listOrganizations({ team: true });

const resource = await user.resources.create({
  applicationId: applications[0]!.id,
  scheme: "acme",
  locator: "project-42",
  displayName: "Project 42",
  audience: { type: "organization", organizationId: organizations[0]!.id },
});

await user.resources.update(resource.id, { displayName: "Renamed", listed: false });
await user.resources.requestValidation(resource.id);
const accessible = await user.resources.listAccessible({ scheme: "llm" });
const catalogue = await user.resources.getCatalogue();
```

| Method | Description |
| --- | --- |
| `listOwned()` | The resources the user owns, with their active grant count. |
| `getResource(resourceId)` | One resource the user may manage. |
| `create({ applicationId, scheme, displayName, locator?, metadata?, audience? })` | Declares a resource in `pending_validation`. `audience` shares it in the same call. |
| `update(resourceId, { displayName?, listed?, metadata? })` | At least one field is required. |
| `delete(resourceId)` | Deletes the resource for good, with its grants; returns the `Resource`. `RES_019` while the relay still serves the model. |
| `requestValidation(resourceId)` | Asks the scheme's validator to check ownership; returns `{ resource, validatorUrl, validationCommand }`. |
| `listGrants(resourceId)` | The resource's grants, each with its `permission`. |
| `createGrant(resourceId, { subjectType, subjectId?, subjectEmail?, permission?, expiresAt? })` | Shares the resource. `subjectType` is `user`, `organization`, `plan`, `everyone` or `application` (`subjectId` is the slug). A `user` subject takes an id or an e-mail, never both; `permission` is `read` (default) or `write`; `expiresAt` must be in the future. |
| `updateGrant(resourceId, grantId, { permission })` | Changes the level of an active grant without revoking it (`RES_014` when the scheme does not support the level, `RES_015` for an inactive grant). |
| `revokeGrant(resourceId, grantId)` | Revokes a grant; the row stays as history. |
| `deleteGrant(resourceId, grantId)` | Deletes a revoked or expired grant for good (`RES_020` for an active one). |
| `shareWithApplication(resourceIds, { applicationSlug, permission?, expiresAt? })` | Shares up to 100 resources with one application; returns one `{ resourceId, grantId, code }` per resource, `code` being the refusal. |
| `listAccessible({ scheme?, applicationId? })` | The validated resources the user may use through the calling application, each with its `permission`: a listing filter, not an admission. |
| `getCatalogue()` | The applications and resources offered to the user, with the enabled schemes. |
| `listMemberApplications()` | The applications the user belongs to that have resource sharing on. |

Every input is validated before any request (`CFG_001`): ids are UUIDs, `scheme` matches
`^[a-z][a-z0-9]{0,49}$`, `displayName` is 1 to 200 characters after trimming, `locator` 1 to
255, `metadata` is at most 4 KiB, and a grant names either `subjectId` or `subjectEmail`, with
`expiresAt` in the future. The organizations used as an audience come from
`user.organizations` ([Teams](/docs/guides/teams)); the listing accepts either the
`resources:self:manage` or the `organizations:self:manage` scope.

## Verify resource webhooks

auth-service can deliver signed `resource.grant.created`, `resource.grant.revoked`,
`resource.grant.updated` (a level change) and `resource.deleted` events to
the application's webhook URL. Verify them with `verifyResourceEvent` from
`@circle-rd/auth-ai/server` before parsing anything else:

```ts
import { verifyResourceEvent } from "@circle-rd/auth-ai/server";

const event = await verifyResourceEvent(request.headers, rawBody, {
  secret: process.env.RESOURCE_WEBHOOK_SECRET!,
});

if (event.type === "resource.deleted") {
  await dropResource(event.resource.id);
} else {
  await syncGrant(event.grant, event.recipients);
}
```

The header is `t=<unix seconds>,v1=<hex HMAC-SHA256>`, computed over `<t>.<raw body>` with the
application's webhook secret. Pass the **raw** body, before any JSON parsing. The timestamp must
be within five minutes by default (`toleranceSeconds`); a stale or tampered delivery throws
`REQ_001`. Deduplicate on `event.eventId`: a retry can deliver the same event again.

## Errors

| Situation | Error |
| --- | --- |
| Invalid input (id not a UUID, empty subject, reason too long) | `CFG_001`, before any request |
| Scope not granted | `TOK_004`, `details.scope` |
| auth-service refused (`AUTH_011`, `RES_001`, `RES_004`…) | `API_001`, `details.status` and `details.apiCode` |
| Unexpected answer | `API_002` |
